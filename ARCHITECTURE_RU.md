# Архитектура Pyra

## Почему Python + нативные компоненты

Python отвечает за связи между компонентами и интерфейс высокого уровня.
Текстовый буфер, лексер, выделение и прокрутка реализованы в QScintilla на C++.
Qt рисует интерфейс без браузерной оболочки. Это позволяет быстро развивать
приложение и проверять реальные расходы памяти до переноса отдельных частей
на другой язык. Решение о дальнейшем переносе стоит принимать по профилю.

`ActivityRail` связывает кнопки навигации с существующими действиями окна;
состояние отслеживается по переключению вкладок, видимости панелей и смене фокуса.
`LayoutController` уведомляет навигацию при показе, отделении и возврате инструментов.
Иконки рисует `QIconEngine` средствами `QPainter` при нужном масштабе: отдельные
шрифты, SVG-библиотеки и файлы ресурсов не нужны. Одиночный отложенный вызов
объединяет события show/hide; периодического опроса и анимаций нет.

Jedi работает последовательно в одном процессе: его быстрый parser нельзя
безопасно разделять между потоками. При превышении 15 секунд процесс анализа
перезапускается. Запросы несут идентификатор вкладки, ревизию и позицию курсора;
результат применяется только к соответствующей версии документа.
Фоновому процессу задаётся пониженный приоритет. Модуль Jedi загружается только
при первом семантическом запросе: структуре файла нужен лишь стандартный AST.
Если Python проекта новее Python самой IDE, AST разбирается отдельным вызовом
выбранного интерпретатора с ограничением 5 секунд. Исходник передаётся через stdin
и никогда не исполняется для построения структуры.

Ruff получает несохранённый текст через stdin. Его stdout и stderr разделены,
чтобы сообщения об ошибках и предупреждения никогда не попадали в исходный код.
Вызывается бинарник Ruff из окружения IDE; `python -m ruff` используется только
как резервный путь. Целевая версия языка берётся из выбранного Python проекта.
Версия кешируется в настройках и читается из `pyvenv.cfg`, чтобы не запускать
дополнительный процесс Python для отображения версии при старте окна.
Вызовы pip получают аргументы отдельным списком, без shell. Программа пользователя
запускается в PTY, поэтому работают `input()`, сигналы терминала и цветной вывод.
Очередь непрочитанного вывода ограничена восемью чанками по 32 КиБ; история — 3000 строк.
Обычный Run не ждёт диагностики и не поднимает отладчик. Создание окружения
и pip используют выбранный Python проекта, а не Python процесса IDE.

Отладчик использует стандартный DAP. Обратный запрос `runInTerminal` запускает
debugpy-launcher в терминале IDE и возвращает PID; код исполняется в выбранном
Python, а пакет debugpy хранится в окружении самой IDE.

## Расширения в будущем

Загрузчика плагинов сейчас нет. Подключение к редактору и сервисам проходит
через Qt-сигналы и отдельные классы. Для добавления расширений сначала следует
зафиксировать контракты `DocumentSnapshot`, `Workspace`, `CommandRegistry`,
`CompletionProvider` и жизненный цикл `activate/deactivate`. Долгие задачи
следует оставлять вне GUI-потока. AI-провайдер, language server и расширения
могут быть отдельными сервисами с явной настройкой; они не нужны для запуска IDE.

Плагины не должны получать прямой доступ к внутренним виджетам окна: это
позволит менять интерфейс без поломки API и контролировать ресурсы расширений.
В этот архив такой API намеренно не включён как якобы готовая функция.

### Разделение runtime

В исходниках Qt/Jedi/debugpy используют окружение IDE; исполняемый код — выбранный
Python проекта. В собранном приложении Qt остаётся встроенным; Jedi и адаптер
отладки запускаются выбранным Python с `-I` и загрузчиком из комплекта. `-I`
не позволяет каталогу проекта или PYTHONPATH подменить служебные модули. Затем
Jedi анализирует проект явно через свой API. Пользовательский код не импортируется
для построения AST. Исходники служб располагаются в `services/`, отдельно от Qt.

Это устраняет необходимость восстанавливать отсутствующие stdin/stdout в
Windows --windowed и исключает рекурсивный запуск GUI как Python. debugpy
принудительно использует pure-Python fallback; иначе его двоичные расширения
могли бы соответствовать версии сборщика, но не версии Python проекта.
Изолированные службы используют стандартные PIPE/QProcess; интерактивные
программы — прежний ConPTY/PTY. Переход на пайпы не затрагивает Run/input().

В Linux для внешних программ восстанавливаются LD_LIBRARY_PATH/LIBPATH_ORIG;
в Windows после загрузки Qt сбрасывается SetDllDirectoryW. Сброс однократный:
нет конкурирующих временных изменений глобального пути DLL из разных потоков.
PATH очищается от путей комплекта; Python проекта и VIRTUAL_ENV задаются явно.
На Windows требуется отдельная проверка Qt plugin loading и ConPTY; Linux её
не заменяет. Официальное описание поведения упаковщика:
https://pyinstaller.org/en/stable/common-issues-and-pitfalls.html

### Жизненный цикл и хранение

В settings.json добавлены `interpreters` (проверенные сведения) и
`default_interpreter`. Существующее projects[path].interpreter остаётся основным
выбором проекта. Файлы настроек записываются прежним атомарным механизмом.
Ошибка валидации не меняет выбор; для venv сохраняется выбранный путь без resolve.
Проверка Python выполняется QProcess, таймаут — 5 с. Поиск: до 48 кандидатов,
бюджет 12 с, отдельная проба до 2 с, Launcher до 3 с. Это бюджет обработки,
не строгая гарантия для подвисшего сетевого/системного I/O; рекурсивного сканирования
дисков нет, сетевые и съёмные диски автоматически не обходятся.

Смена окружения/проекта сбрасывает очередь Jedi и завершает старый процесс;
новые запросы ждут finished перед запуском следующего. Результаты pip list
проверяют исходный интерпретатор. Во время запуска/отладки/установки пакетов
переключение запрещено. Уже открытые интерактивные shell сохраняют свой Python;
новые используют новое окружение.

Ротация журнала: текущий файл до 1 МиБ и три предыдущих. В диалоге читается
последний фрагмент до 64 КиБ. Нет автоматической выгрузки окружения или исходников.
Поиск завершается до уничтожения QThread; окно не уничтожает работающий поток.
Полная декомпозиция MainWindow и расширение workspace относятся к v0.3.

## Изменения v0.3: сессия и жизненный цикл

GUI читает QScintilla только в главном потоке. SessionController кеширует текст по
паре token/revision и передаёт обычный снимок данных CheckpointWriter. Один QThread
с Condition держит максимум одну текущую и одну последнюю ожидающую запись.
JSON, резервная копия и атомарная запись выполняются в этом потоке. Debounce 1000 мс
и периодический таймер 5000 мс обеспечивают сохранение при паузе и непрерывном вводе;
в простое записи нет. Подтверждённый выход ждёт последнюю запись до пяти секунд,
ошибка/таймаут отменяет выход. Это контрольные точки, а не гарантия сохранения каждого
последнего символа при отключении питания. Общий JSON ограничен 256 МиБ.

WorkspaceStore не пишет исходники. При восстановлении применяются буфер, кодировка,
LF/CRLF и сохранённый mtime; сохранение поверх внешнего изменения требует подтверждения.
Утерянный исходный путь не мешает восстановить черновик. Закрытие отдельной вкладки
по-прежнему явно подтверждается; закрытие приложения использует сохранённые черновики.
QLockFile из app.py запрещает две одновременно пишущие сессии.

TaskRegistry хранит ссылки на функции состояния, отмены и завершения; QObject/QThread
остаются у своих сервисов. На выходе блокируется редактирование, останавливаются таймеры,
заканчиваются/отменяются процессы и потоки. Незавершённый QThread не уничтожается:
окно повторяет проверку завершения через 200 мс. TaskRegistry не отменяет запись сессии.
QProcess Job на Unix создаёт отдельную сессию; отмена завершает её process group.
В Windows taskkill /T видит ещё живого родителя, затем действует резервный kill.

Поиск проверяет отмену между файлами и строками, игнорирует результаты старого проекта
и удаляет завершённый worker. Regex использует уже имеющийся Qt/PCRE2:
`(*LIMIT_MATCH=100000)(*LIMIT_DEPTH=1000)`. Превышение лимита показывается пользователю;
буквальный поиск использует обычное сравнение строк. Синтаксис Regex — PCRE2,
редкие Python-re-специфичные конструкции могут отличаться. Описание ограничений:
https://www.pcre.org/current/doc/html/pcre2pattern.html
https://doc.qt.io/qt-6/qregularexpression.html

RuffService принимает неизменяемый DocumentSnapshot, объединяет ожидающие проверки,
при отмене сбрасывает адресатов результатов. MainWindow дополнительно сверяет token
и revision перед применением. Форматирование: `ruff check --select I001 --fix-only
--no-unsafe-fixes` в stdin, затем `ruff format`; единственная правка редактора идёт
после успеха обеих стадий. stdout и stderr никогда не смешиваются.

LayoutController сохраняет геометрию, QMainWindow state версии 3, размеры splitters,
видимость и активную панель. Стандартный компактный QTabWidget сохраняется; панели
отделяются в именованные QDockWidget по запросу. Focus сохраняет обычную компоновку
перед скрытием панелей. Закрепление не блокирует QTabBar.tabMoved для внутреннего
стека QTabWidget: подписи и виджеты перемещаются вместе.

Консоль явно задаёт установленный fixed-pitch шрифт поверх общего QSS и измеряет
уже применённый шрифт. Выделение — полуоткрытый диапазон ячеек; при его начале
сохраняется ограниченный снимок видимого экрана. Вывод продолжает поступать в pyte.
Подсветка выделения не меняет границы текстовых runs. Не-ASCII-глифы размещаются
по ячейкам; продолжение широкого глифа не затирает его правую половину. История
осталась ограниченной 3000 строками, очередь вывода — восемью чанками.
